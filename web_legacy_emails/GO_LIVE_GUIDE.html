Run the workflow in test mode

7b

Reliable trigger: Google Apps Script

~15 minutes once · github.com + script.google.com

GitHub's own timer is best-effort — for this repository it skipped most slots (1 run in ~20). A small Google Apps Script in your account therefore starts the workflow (same as Run workflow) on your SEND_DAYS at SEND_TIME, checking every 10 minutes. It reads those GitHub variables, so you still change day/time only on GitHub. GitHub's timer stays as a free backup; the "sent today" marker prevents double emails.

7b-1. Create a GitHub token that can only start this workflow

  1. github.com → your avatar (top right) → Settings → Developer settings (bottom of the left menu) → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Token name: web-legacy-emails trigger · Expiration: the longest allowed (e.g. 1 year — note the date; see "Everyday changes").
  3. Resource owner: rahulshettycropin · Repository access: Only select repositories → web_legacy_emails.
  4. Permissions → Repository permissions: Actions → Read and write and Variables → Read-only. Leave everything else as "No access" (Metadata read-only is added automatically).
  5. Generate token → copy it (starts with github_pat_). It is shown only once.
What this token can doStart this repository's workflows and read its variables — nothing else. It cannot read your code or your Secrets, and it can't touch other repositories.

7b-2. Create the Apps Script project

  1. Open script.google.com (the Google account that should own the trigger) → New project.
  2. Click "Untitled project" at the top → rename to Web Legacy Emails trigger.
  3. In Code.gs, delete everything and paste the full contents of web_legacy_emails/apps_script/github_trigger.gs from the repository (open it on github.com → Raw → Ctrl+A, Ctrl+C) → Save (💾).
  4. ⚙️ Project Settings (left bar) → scroll to Script properties → Add script property → Property GITHUB_TOKEN, Value = the token from 7b-1 → Save script properties.

7b-3. Check, then switch on

  1. Back in the Editor (<> icon): in the function dropdown next to ▶ Run choose testCheckNow → ▶ Run.
  2. First time only, Google asks for permission: Review permissions → pick your account → "Google hasn't verified this app" → Advanced → Go to Web Legacy Emails trigger (unsafe). It is your own script, so "unverified" is expected.
  3. On "Select what Web Legacy Emails trigger can access", tick both checkboxes (or Select all) → Continue:
    • Connect to an external service — needed to call GitHub (read SEND_DAYS / SEND_TIME, start the workflow).
    • Allow this application to run when you are not present — needed for the 10-minute trigger to run with your PC and browser closed.
    Leaving either unticked makes the script fail. It asks for nothing else (no Gmail, Drive or contacts access).
  4. The Execution log shows e.g. Wed 17:40 (Asia/Kolkata) · slots: Wed 17:00 [send] · due: 1 and Would dispatch: … — nothing has been sent.
  5. Optional: run testDispatchNow → the Actions tab shows a new run in mode test → a [TEST] email arrives. This proves the token works.
  6. Careful: if today is a send day and SEND_TIME has passed, the first check after setup (within 10 minutes) sends today's real email and saves today as a week. Don't want that? Set WEEKLY_EMAIL_ENABLED = false or change SEND_DAYS first — or delete the test week afterwards (see "one flow for every update" at the end).
  7. Run setup once → the log says Trigger created: checkAndDispatch every 10 minutes. ⏰ Triggers (left bar) now lists it. Done — it runs by itself from now on, even with your PC off.
Watching it⏰ Triggers → ⋮ on the trigger → Executions lists every check (most say due: 0). Google emails you about failures; on the trigger you can set failure notifications to Notify me immediately. On GitHub, runs started by the script show as "Manually run by <your GitHub user>" with mode scheduled.
Several times a day (other projects)Change schedule: 'github' at the top of the script to a list, e.g. schedule: [{ days: 'Mon-Fri', times: '10:00, 13:00, 17:00' }] — each time is started once per day, within 10 minutes. Days accept Mon, Mon,Fri, Mon-Fri, *. Point owner / repo / workflowFile / inputs at the other workflow. To stop: run remove.

Test the scheduled send (to you only)

~5 minutes · on github.com · no file edits, no waiting

This tests the automatic path — the same logic the timer uses — with test-only settings.

Settings → Secrets and variables → Actions → Variables tab → New repository variable

NameValue for the testMeaning
SCHEDULE_MODEtestScheduled runs send a [TEST] email only to GMAIL_USER and don't touch history
SEND_DAYSToday, e.g. TueDays to send: Mon Tue Wed Thu Fri Sat Sun — several with commas
SEND_TIMEThe current time or earlier, e.g. 16:00IST, 24-hour. "At or after" this time — so a time already passed means it's due right away (e.g. 00:00 for any time today)
WEEKLY_EMAIL_ENABLEDtrue (lower case)Master switch for scheduled sending

Run it now — no waiting (recommended)

  1. Actions → Web Legacy Emails – Weekly Summary → Run workflow → mode scheduled → Run workflow.
  2. This runs exactly what a timer wake-up runs — the due check with your SEND_DAYS / SEND_TIME, then SCHEDULE_MODE, the "sent today" marker and the commit — just immediately, at any time of day.
  3. Open the run → step Is a send due now? says Due (…) → your inbox gets the [TEST] email.
  4. Run scheduled once more: it now says Already sent today — proof it sends only once per day.

Optional: also watch the real timer

  1. The timer wakes at :00 and :30 past each hour between 15:30 and 00:00 IST. GitHub often starts them late — 5–20 minutes usually, occasionally hours (a 00:00 slot was seen starting at 01:48).
  2. Runs before your SEND_TIME say Too early; the first after it sends; later ones say Already sent today.
  3. A late run after midnight (before 06:00 IST) still counts as the previous evening, so a delayed Friday slot still sends Friday's email.
Why "wake-ups"?GitHub's timer (the cron: line) is fixed and can't read variables, so the workflow wakes every 30 minutes in this evening window and checks SEND_DAYS / SEND_TIME. You never edit the file — only the variables. A SEND_TIME earlier than 15:30 sends at the first wake-up (~15:30). Need morning sends? Ask to widen the window.
Test again the same day?Delete web_legacy_emails/last_scheduled_send.json in the repository (open it on github.com → ⋯ → Delete file). A test send never blocks a real send on the same day.

read the step output in the run: "Is a send due now?" first, then "Send weekly summary"
Message / symptomFix
No email on the send day (Apps Script set up)script.google.com → the project → Executions: slots: none (disabled) → WEEKLY_EMAIL_ENABLED isn't true; HTTP 401/403 → token expired or missing a permission (Step 7b-1); GITHUB_TOKEN is not set → Step 7b-2. If it says Dispatched, open the GitHub run ("Manually run by …", mode scheduled) and read Is a send due now?.
No Scheduled runs at allOpen .github/workflows/web-legacy-emails-weekly.yml on GitHub: the cron line must be '0,30 10-18 * * *'. If not, the latest workflow wasn't pushed — run git add . in the deploy folder's root, commit, push. Also check Actions are enabled (Step 5).

Green runs but no emailOpen the run → Is a send due now?: Not a send day (check SEND_DAYS), Too early (check SEND_TIME, IST), Already sent today (delete last_scheduled_send.json to resend). Runs between 00:00 and 06:00 IST are judged as the previous evening and say "late run".
Unknown day in SEND_DAYS / SEND_TIME must be HH:MMFix the variable: days like Fri or Mon,Fri; time like 17:30.
Jira email and API token are not configuredJIRA_EMAIL variable or JIRA_API_TOKEN secret missing or misspelled.

Gmail address and app password are not configuredGMAIL_USER variable or GMAIL_APP_PASSWORD secret missing.
Gmail rejected the loginUse a Google App Password (not the normal password) created for the same account as GMAIL_USER; 2-Step Verification must be on.

Very important: one flow for every update — pull, edit, push

main project = My dashboard · deploy folder = web_legacy_emails_deploy (the GitHub repo)

GitHub adds a new week to the deploy repo after every real send. Use this same flow for everything — bringing those weeks back, deleting or correcting a week, changing code or docs, or any mix of them. Skip the parts you don't need.

  1. Pull — double-click My dashboard\web_legacy_emails\deploy\sync_pull.bat.
    • Runs git pull in the deploy folder, then brings GitHub's new weeks into the main project (the old history file is backed up to your temp folder).
    • Expect [HISTORY] base: +N week(s) from GitHub: … when emails were sent since the last pull, and [DIFF] lines for any code/docs you already changed (just a report — nothing is overwritten).
  2. Delete or correct a week (optional) — in the main project:
    • Dashboard (easiest): Web legacy emails → ✏️ Edit / Trend Data → All Weeks table → 🗑️ on the date (or change its numbers) → Save Table Changes; or
    • File: edit My dashboard\web_legacy_emails\jira_weekly_history.json (delete the whole { "date": "…", … } entry, watch the commas), save.
  3. Change code / config / docs (optional) — in the main project, as usual. Steps 2 and 3 can happen in any order, even before step 1.
  4. Push — double-click My dashboard\web_legacy_emails\deploy\sync_push.bat.
    • Runs git pull in the deploy folder first, then copies your changes. Expect [COPY] … for changed files and, if you deleted/corrected weeks, [HISTORY] deploy: −1 deleted in base: … / … corrected in base: ….
    • If GitHub sent an email after your pull, you'll see [INFO] GitHub has 1 week(s) base doesn't … — kept: that week is safe; the next pull brings it to the main project.
  5. Commit and push the deploy folder — straight away: 
    cd "C:\Users\rahul.shetty\Documents\Important\AntiGravity\web_legacy_emails_deploy"
git status
git add .
git commit -m "Describe your change"
git push
    git status should list only what you changed (plus web_legacy_emails/jira_weekly_history.json if you deleted/corrected a week).

How the history stays safe

Each pull saves a snapshot of GitHub's history (local file deploy\last_pull_snapshot.json). On the next push or pull every week is compared with that snapshot:

WeekResult
Deleted in the main project since the last pullRemoved from GitHub too
Numbers corrected in the main project, GitHub's copy unchangedYour numbers win
Sent by GitHub after your last pullAlways kept (never lost)
Changed on both sidesGitHub's numbers win (that is what was emailed) — shown as [WARN]
Only in the main projectAdded to GitHub
Before deleting a week, pull at least once on this PCThe snapshot is created by sync_pull.bat. Without it (e.g. a new laptop), the first push only adds weeks and never deletes — it says no pull snapshot yet. Run sync_pull.bat, then delete again and push.
git push rejected ("fetch first")?GitHub committed something between step 4 and step 5. Run sync_pull.bat → sync_push.bat again, then step 5. Never force-push.
Same-day markerA send also writes web_legacy_emails/last_scheduled_send.json in the deploy repo ("already sent today"). Leave it — it only blocks a second send on that same date.

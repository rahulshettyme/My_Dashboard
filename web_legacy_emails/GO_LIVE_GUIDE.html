Before you start: use fresh credentials Until Oct 20, 2026 the dashboard could expose the Jira token and Gmail app password to other machines on the network. Create a new Jira API token and a new Google App Password for GitHub, then delete the old ones (Jira: id.atlassian.com → Security → API tokens · Google: myaccount.google.com → Security → App passwords).
What you need ready A GitHub account · the new Jira API token · the new Google App Password · your Atlassian login email · the Gmail address that sends the email · 20–30 minutes.
1

Create a private repository on GitHub

~2 minutes · on github.com
  1. Go to github.com/new.
  2. Repository name: web-legacy-emails (any name works).
  3. Choose Private. The config contains recipient emails and the Jira queries contain team account IDs.
  4. Leave Add a README, .gitignore and license unticked — the deploy folder already has them, and an empty repo avoids a merge conflict on the first push.
  5. Click Create repository. Keep the page open; you need its URL (e.g. https://github.com/your-name/web-legacy-emails.git).
Company GitHub organisation? If you create it under a Cropin organisation instead of your personal account, an admin may need to allow GitHub Actions there (see Step 5).
2

Refresh the deploy folder and push it

~5 minutes · on your PC

2a. Refresh the deploy folder

Double-click web_legacy_emails\deploy\sync_push.bat in the main dashboard project (or run the command below from the project folder). It copies only this module's files and never copies passwords.

2b. Push it to GitHub (first time only)

Open Command Prompt and run these one by one. Replace the URL in the 5th line with your repository's URL from Step 1.

3

Add the 2 Secrets (token and password)

~3 minutes · on github.com

Your repository → Settings → Secrets and variables → Actions → Secrets tab → New repository secret

Create these two, one at a time (Name exactly as shown, then paste the value, then Add secret):

NameValue
JIRA_API_TOKENThe new Jira API token (starts with ATATT)
GMAIL_APP_PASSWORDThe new 16-character Google App Password (spaces don't matter)
Why Secrets and not Variables?Secrets are encrypted and hidden as *** in run logs. Nobody — including you — can read them back after saving; to change one, just add it again with the same name.

5

Allow GitHub Actions to run and to save history

~1 minute · on github.com

Your repository → Settings → Actions → General

  1. Actions permissions: "Allow all actions and reusable workflows" (or at least "Allow actions created by GitHub" — the workflow only uses GitHub's own actions).
  2. Scroll to Workflow permissions → choose Read and write permissions → Save. This lets the workflow commit the new week to jira_weekly_history.json after each real send.
Options greyed out?Your organisation controls them — ask a GitHub admin to allow Actions with write permission for this repository.
6

Run the workflow in test mode

~3 minutes · on github.com + your inbox
  1. Open the Actions tab of your repository. If GitHub asks, click "I understand my workflows, go ahead and enable them".
  2. In the left list, click Web Legacy Emails – Weekly Summary.
  3. On the right, click Run workflow → Branch main → mode test → green Run workflow button.
  4. Refresh after a few seconds. A new run appears with a yellow dot (running). It takes about 1–2 minutes.
  5. A green tick means success. Check the inbox of GMAIL_USER for an email whose subject starts with [TEST].

What test mode does: fetches live counts from Jira, draws the charts, sends only to the Gmail account itself, and does not change the history.

Red cross?Click the run → weekly-summary → expand Send weekly summary. The last line says what failed — see the Troubleshooting table at the bottom.
7

Run the workflow in dry-run mode

~3 minutes · on github.com
  1. Actions → Web Legacy Emails – Weekly Summary → Run workflow → mode dry-run → Run workflow.
  2. When it is green, click the run. Scroll to Artifacts at the bottom and download email-preview (a .zip).
  3. Unzip it and open last_scheduled_preview.html in your browser — this is exactly what the team will receive.

What dry-run does: builds the full email but sends nothing and saves nothing.

8

Test one scheduled send (to you only)

~3 minutes setup + up to ~45 minutes waiting · on github.com · no file edits

This proves the automatic path: GitHub starts the run by itself — you don't click anything.

Settings → Secrets and variables → Actions → Variables tab → New repository variable

NameValue for the testMeaning
SCHEDULE_MODEtestScheduled runs send a [TEST] email only to GMAIL_USER and don't touch history
SEND_DAYSToday, e.g. TueDays to send: Mon Tue Wed Thu Fri Sat Sun — several with commas
SEND_TIMEThe current time or earlier, e.g. 16:00IST, 24-hour. "At or after" this time — so a time already passed means the next wake-up sends
WEEKLY_EMAIL_ENABLEDtrue (lower case)Master switch for scheduled sending

Then wait and watch

  1. Open the Actions tab (Event filter → schedule). GitHub wakes the workflow at :00 and :30 past each hour between 15:30 and 00:00 IST, often 5–20 minutes late. Each wake-up appears as a Scheduled run.
  2. Open the first one → step Is a send due now? says Due (…), then it installs and sends. Your inbox gets the [TEST] email.
  3. Later wake-ups that day finish in seconds with Already sent today — proof it sends only once.
Why "wake-ups"?GitHub's timer (the cron: line) is fixed and can't read variables, so the workflow wakes every 30 minutes in this evening window and checks SEND_DAYS / SEND_TIME. You never edit the file — only the variables. A SEND_TIME earlier than 15:30 sends at the first wake-up (~15:30). Need morning sends? Ask to widen the window.
Test again the same day?Delete web_legacy_emails/last_scheduled_send.json in the repository (open it on github.com → ⋯ → Delete file). A test send never blocks a real send on the same day.

Do Step 10 right awayOtherwise your PC schedule and GitHub can both send and the team gets two emails.
10

Turn off the schedule on your PC

~1 minute · local dashboard
  1. Open the dashboard → Web legacy emails → 📧 Email.
  2. Scroll to 📅 Scheduled Sending → untick "Send automatically on schedule" → Save Schedule.
  3. The status line must say ○ Off — nothing will be sent automatically.

The dashboard still works for viewing live counts, editing history and the manual Send Email (Gmail compose) button.

Troubleshooting

read the step output in the run: "Is a send due now?" first, then "Send weekly summary"
Message / symptomFix
No Scheduled runs at allOpen .github/workflows/web-legacy-emails-weekly.yml on GitHub: the cron line must be '0,30 10-18 * * *'. If not, the latest workflow wasn't pushed — run git add . in the deploy folder's root, commit, push. Also check Actions are enabled (Step 5).
Scheduled runs show grey "skipped"WEEKLY_EMAIL_ENABLED missing or not exactly true.
Green runs but no emailOpen the run → Is a send due now?: Not a send day (check SEND_DAYS), Too early (check SEND_TIME, IST), Already sent today (delete last_scheduled_send.json to resend).
Unknown day in SEND_DAYS / SEND_TIME must be HH:MMFix the variable: days like Fri or Mon,Fri; time like 17:30.
Jira email and API token are not configuredJIRA_EMAIL variable or JIRA_API_TOKEN secret missing or misspelled.
Jira rejected the email/API tokenToken expired or wrong, or JIRA_EMAIL isn't the Atlassian login email. Create a new token and replace the secret.
Gmail address and app password are not configuredGMAIL_USER variable or GMAIL_APP_PASSWORD secret missing.
Gmail rejected the loginUse a Google App Password (not the normal password) created for the same account as GMAIL_USER; 2-Step Verification must be on.
No "To" recipients configured / Invalid email addressCheck EMAIL_TO / EMAIL_CC for typos; separate with commas.
Commit history step fails with 403 / permission deniedStep 5: set Workflow permissions to "Read and write". Check branch protection rules on main.
git push on your PC is rejected ("fetch first")GitHub has newer commits (history / marker). Run git pull, then push again.
npm ci step failsThe lock file is out of date: run sync_push.bat again (it regenerates package-lock.json), then commit and push.
Team got two emailsThe PC schedule is still on — Step 10.
